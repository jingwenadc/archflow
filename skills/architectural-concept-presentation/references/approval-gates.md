# 内容对齐与范围协作

目标是在人类确认方向和内容后再花时间生成视觉。保留两个必要内容确认点；制作顺序和章节分工保持灵活。

## 1. 纯文字议程

提交简短 Markdown：给谁看、希望对方选择什么、一句话主张、章节顺序与任务、大致篇幅、已有资料、会改变方向的缺口。此时不细写每页，不创建页面、图像或生成代码。等待议程确认。

## 2. 纯文字逐页内容

议程确认后，为约定范围的每一页写出实际标题、拟上屏短文案、图像/图解表达的关系与制作方法、来源与设计提案状态、待补资料和希望受众记住的价值。使用 [逐页模板](storyboard-and-modules.md)。

规划新图时只写文字，不执行图像生成或制作幻灯片。提交后等待确认。完整新稿覆盖全稿后再制作；局部工作继承已有整体方向，只确认相关内容，不要求用户为一章重新批准整份文稿。

## 如何识别批准

用户直接回应刚展示的唯一明确提案说“可以，就按这个做”，可视为确认。同一条消息明确批准内容并要求制作某章，不再重复询问范围。已有版本明确获批时直接继承。

“继续”是否构成批准取决于上下文：如果上一条只在等待对某份内容的确认，可以认可；若仍有多个方案或不知道批准对象，只问尚未解决的选择。沉默、上传材料或局部意见，不等于批准所有内容。

批准应指向具体文件版本或稳定页 ID 集合，并有用户消息/人工记录作为依据。示例状态不是批准记录，复制示例不得解锁制作。

## 3. 按范围制作

开始前简要说明继承的内容版本、本次范围和保存位置，在已有授权内完成。可任选章节顺序、跨页分组或并行，不增加逐图/逐页批准的固定步骤。

先在授权范围内用主视觉页和图解页校准风格，再完成该范围。单页任务只做该页。除非用户要求先看样式，或发现方向冲突，不把风格校准变成第三道固定审批。

状态文件统一放在：

    方案工作区/00_项目总控/project-state.json

需要脚本检查时执行：

    python <技能目录>/scripts/check_project_gate.py <状态文件> --action generate-section --section <范围编号>

structure 记录继承的议程批准，storyboard 记录本次交付范围的内容批准；为局部任务建立局部状态，不把它误记为全稿批准。完整整合使用覆盖所选全部范围的状态。

脚本是辅助检查，不是批准来源或可信安全边界。没有执行能力时按相同规则核对真实批准，不伪称已经运行。需要硬性执行的宿主必须在工具调用层校验人工批准，模型不能批准自己的草稿。

## 修改、跳转与并行

- 字体、构图、裁切、同义短文案等不改变批准含义的调整，在现有授权内完成。
- 改变卖点、关键事实、设计方向或范围，先文字列出变化，确认受影响部分再继续。
- 用户仅要求移动已批准页面、不改变论证与内容时，移动指令就是授权；无关章节继续有效。
- 多个对话读同一有效议程、故事板和视觉约定，各写不同范围目录。主对话/协调者更新总控，其他对话提交版本记录，避免同时覆盖总控。
- 修改已选定版本时另存新版，只影响真正依赖该变化的页面。

## 文件与整合

    方案工作区/
    ├── 00_项目总控/       # 素材索引、批准依据、视觉约定、版本清单
    ├── 01_整体框架/       # v01.md、v02.md
    ├── 02_逐页故事板/     # 全稿或分章 Markdown；可选 JSON
    ├── 03_章节设计/       # 每个范围各自保存 v01、v02
    ├── 04_整合版本/
    └── 05_终稿交付/

已有项目结构可映射沿用，所有对话共用同一个根目录。每个制作版本保存源文件、图片、PPTX 与实际可生成的预览，不能覆盖已交付版本。版本清单记录范围、依据的内容版本、修改、文件链接及用户选择。

最终整合只使用用户选定版本。部分内容仍在修改时可交付已完成部分，不冒充全稿。缺失事实只阻塞依赖它的页面；缺视觉素材时先按图解创作规则设计示意，不自动阻塞整个任务。
